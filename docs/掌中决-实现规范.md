## 1. 合规设计规范（本文件最重要的部分）

> 判定标准是**页面实际提供什么服务，不是文案怎么写**（《常见拒绝情形》3.2.4）。所以下面的规范不是"换词游戏"，而是**改服务形态**。

### 1.1 产品定位话术（对外统一口径）

**一句话定位**：
> 掌中决是一个**决策辅助工具**：当你在几个选项之间拿不定主意时，它用一套传统的六宫框架，随机给你一个选择和一个换角度的提醒，帮你把决定做掉。

**必须出现的定位说明**（结果页常驻，小字）：
> 这是一次随机提示，帮你换个角度看问题，不是预测。

⚠️ **注意不要写「仅供娱乐」**——那是免责声明式的敷衍，既无豁免效力（微信没有任何条款支持它），又让产品显得心虚。**写诚实的产品说明。**

### 1.3 六宫命名策略：双层

| 层 | 用什么名字 | 说明 |
| --- | --- | --- |
| **功能层**（结果主线） | **中性情境词**：稳 / 缠 / 快 / 争 / 合 / 空 | 用户第一眼看到的是「情境」，不是「卦」 |
| **文化层**（副标题 + 科普页） | 传统名：大安 / 留连 / 速喜 / 赤口 / 小吉 / 空亡 | 作为传统文化知识呈现，注明出处与含义 |

这样既保住了你要的「传统文化核心」，又让功能主线读起来是**情境分析**而不是**断卦**。

### 1.4 五条不可越界的红线

1. **不预测**：任何输出都不得断言「这件事会怎样」。只说「这件事现在处于什么局面 + 你能做什么」。
2. **不判吉凶**：没有好坏，只有情境差异。
3. **不索取隐私**：不要生辰八字、不要姓名、不要照片、不要位置。**这条尤其重要**——2024-08 微信专项公告点名打击「采集用户姓名、生辰八字、面/手相」。
4. **不收费**：零付费、零广告、零解锁。付费算命是**独立的驳回理由**，且 iOS 禁虚拟支付。
5. **不诱导分享**：分享必须完全自愿、零奖励。

### 1.5 v1 的功能边界（这条直接决定合规性）

| 场景 | 做不做 | 为什么 |
| --- | --- | --- |
| **选项裁决**（今天吃什么 / 谁洗碗 / 周末去哪，输入 2~3 个选项 → 出一个） | ✅ **做** | 本质是随机选择器，是**工具**。这是 v1 的**唯一**功能 |
| **情境提示**（出一个情境 + 一段提醒 + 一个可执行动作） | ✅ 做 | 是决策辅助的自然延伸 |
| **文化科普**（六宫是什么、掌诀、来历） | ✅ 做 | 纯知识内容，为功能提供文化正当性 |
| 「这件事未来会怎样」 | ⚠️ **做，但只在「扩展层」** | 是占卜特征最强的场景，**不进上架包** |
| 「丢失的东西在哪」 | ⚠️ **做，但只在「扩展层」** | 占卜寻物，**不进上架包** |
| 事业/财运/姻缘走向 | ❌ **不做** | 官方驳回案例里「付费算命」的典型形态，**自用也不做** |

> 📌 **已按你的决策调整为「双构建架构」**——见下面 §1.5.1。

### 1.5.1 双构建架构：内核 / 扩展（你选择「寻物和预测也要」之后的方案）

你的决策：**寻物与走向要做，且接受"可能不能上架"**。架构上不做取舍，做**分层 + 构建期分离**：

| 层 | 内容 | 进入上架包？ | 代码位置 |
| --- | --- | --- | --- |
| **内核** | 选项裁决 + 情境提示 + 文化科普 | ✅ **是** | `data/zhangzhongjue.js` + `pages/zzj/*` |
| **扩展** | 寻物（方位/应期/断辞）、走向（三宫 起·中·果） | ❌ **否，物理排除** | `data/zzj-ext.js` + `pages/zzj/lost.*` + `pages/zzj/future.*` |

**分离机制**：`project.config.json` → `packOptions.ignore`

```json
"packOptions": {
  "ignore": [
    { "type": "file", "value": "miniprogram/data/zzj-ext.js" },
    { "type": "file", "value": "miniprogram/pages/zzj/lost.js" },
    { "type": "file", "value": "miniprogram/pages/zzj/future.js" }
  ]
}
```

微信只审核**实际上传的文件**。被 `packOptions.ignore` 排除的文件**根本不在包里**，所以不构成「隐藏功能」。

#### ⚠️ 唯一不能做的事（这是本质区别，不是措辞问题）

| ❌ 绝对不要 | 后果 |
| --- | --- |
| 运行时开关（某 flag 一开一关） | 运营规范 **5.19 对抗审核** → **永久下架** |
| 审核期间临时隐藏入口 | 同上，且**腾讯有权拒绝再为相关主体提供服务** |
| 判断"是不是审核员"再决定显示什么 | 同上，且**同主体／关联主体累计处罚** |
| 上架前手动删代码、上架后再加回来 | 版本回滚即被扫到，性质等同欺骗 |

**✅ 正确做法**：上架产物里**根本不存在这些代码**——是两套构建产物，不是一套产物两副面孔。

#### 两种用法

| 场景 | 怎么做 |
| --- | --- |
| **现在（自用）** | 什么都不用改，完整内核 + 扩展，开发者工具正常编译预览 |
| **将来（上架）** | 运行 `node tools/build-publish.js`（**待实现**），自动写入 `packOptions.ignore` 并剔除扩展页面注册；跑完 `node tests/check-banned-words.js` 确认内核干净 |

### 1.6 ⚠️ 残余风险声明（请读完再决定）

**我无法给你「必然过审」的保证，原因如下：**
- 3.2.4 的判定由**审核员主观判断**，官方对「正规心理测试算不算」的回复原文是：「**无法提供意见**。审核将以实际提交的小程序服务内容为准」
- 未检索到任何「此类功能包装后成功过审」的公开实证案例
- 你的 App 已有运营历史，一旦被判定违规，处罚是**整个小程序 + 主体**级别（5.7 / 5.19）

**降低风险的三个做法（本规范已内置）：**
1. **功能极度收窄**——只做选项裁决，形态上就是个决策器（§1.5）
2. **词汇全表管控 + 自动化扫描**（§1.2 + §7）
3. **小程序简介同步改写**——审核员会先读简介再进页面，两者必须一致（§8）

### 3.2 抽取算法

```js
// 六宫循环：稳 → 缠 → 快 → 争 → 合 → 空 → (回稳)

// v1 只用「随机数」：无命理输入，零隐私风险，也是最好解释的形态
// 用户可以报 3 个数字，也可以用「摇一摇」产生
function pickByNumbers(n1, n2, n3) {
  const a = ((n1 - 1) % 6 + 6) % 6;        // 负数也安全
  const b = ((a + n2 - 1) % 6 + 6) % 6;
  const c = ((b + n3 - 1) % 6 + 6) % 6;
  return { first: a, second: b, result: c };  // result 就是最终落在的宫
}

// 摇一摇：本地随机，无需服务端
function pickRandom() {
  const n = () => Math.floor(Math.random() * 999) + 1;
  return pickByNumbers(n(), n(), n());
}
```

> **不做农历时间起课**——那需要引入农历算法，且「按生辰/时间推算」正是命理特征。

#### 3.2.1 关于报数流派（必须二选一并在代码注释里写明）

调研发现报数起课有**两个流派**，同一组数字结果不同：

| 流派 | 规则 | 本方案 |
| --- | --- | --- |
| **① 依次传递**（易德轩系） | 第 2、3 个数从**上一次落宫**起数 | ✅ **采用**（与「月上起日、日上起时」的传递逻辑一致） |
| ② 各自起于大安（之法派） | 三个数**各自**从大安起，得前/中/末三宫 | ❌ 不采用 |

代码注释里要写明走的是流派①，方便日后追溯。

#### 3.2.2 传统月日时算法的正确公式（已交叉验证）

虽然 v1 不做时间起课，但公式记在这里，避免日后实现时踩坑：

```js
// 月宫 = (M - 1) % 6
// 日宫 = (M + D - 2) % 6
// 时宫 = (M + D + H - 3) % 6        // H：子=1 … 亥=12
```

**已验证**：三月初五辰时 → **小吉**，与《玉匣记》原文例子一致（本报告第一版给出的公式与此等价，但当时未做实例验证，现已确认）。

> ⚠️ **网上流传一个错误写法**：「(月+日+时) mod 6，余 0 当 6」。用同一输入会得到**不同结果**（三月初五辰时会错算成大安）。代表错误来源：某腾讯云社区的 Java 实现文章。实现时间起课时务必用上面的公式。

#### 3.2.3 两个「全资料无定论」的边界——v1 天然规避 ✅

| 边界 | 状态 | v1 为什么不受影响 |
| --- | --- | --- |
| **晚子时归属**（23:00–24:00 算今天还是明天） | 调研覆盖的全部资料**均未明确** | v1 不用时辰，无影响 |
| **闰月归属** | 资料未明确 | v1 不用农历，无影响 |

**这反过来印证了 v1「只做报数」的范围决策是对的**：它同时规避了合规风险、隐私风险、农历依赖、以及两个定义不清的边界。

### 3.4 ⚠️ 传统断辞素材：可作科普引文，**绝不可进功能层**

配套调研 `docs/小六壬-调研报告.md` 整理了**大量高质量的传统素材**：玉匣记原文断辞、通行口诀、扩展白话歌诀（6 宫 × 约 20 句）、日加时断 120 句、马前失物诀（含**方位 + 拿物人特征**）、分类速断（失物/行人/病人/官非/财/婚）、六壬掌总诀等。

**这些素材极其宝贵，但合规上不能进功能层。** 原因：

| 素材类型 | 样例 | 为什么不能用 |
| --- | --- | --- |
| 吉凶等级 | 大吉／中吉／小凶／大凶 | 直接违反「不判吉凶」红线，且 3.2.3 禁止引发恐惧 |
| **失物方位 + 拿物人特征** | 「失物在坤方，主妇人拿走」 | **这是最典型的占卜内容**，且涉嫌对他人做出无据指认 |
| 疾病类断辞 | 「病人逢暗鬼」「恐怕染瘟殃」 | 直接踩 3.2.3（引发恐惧）+ 3.2.8.7（封建迷信） |
| 官非／血光 | 「官事有刑伤」「赤口主口舌血光」 | 同上 |
| 应期断言 | 「大安 1-7 日应验」 | 属于「预测」，违反红线 1 |

**允许的用法**：
- ✅ 科普页作为**文化知识引文**展示，并注明「传统口诀，属民俗文化内容，本工具不使用其吉凶判断」
- ✅ 作为**文案创作的语感参考**（我们要的是那种凝练的中文质感）
- ❌ 不得出现在功能层的结果页

> 这条必须写进团队约定——否则很容易有人「为了有文化味」把原文断辞直接搬进结果页，**一次就把合规做废**。

## 4. 云函数：不需要（直接回答你的问题）

### 4.1 结论：v1 用纯前端，**不建新云函数**

| 维度 | 纯前端（推荐） | 单独云函数 |
| --- | --- | --- |
| 性能 | 瞬时，无冷启动 | 300ms~2s 冷启动 |
| 成本 | 0 | 云函数调用次数 + 可能的费用 |
| 离线 | ✅ 可用 | ❌ 不可用 |
| 故障点 | 无 | 网络/超时/部署 |
| 逻辑复杂度 | 3 行取余运算 | 3 行取余运算 + 一整套云函数工程 |

**算法本身只有三行取余**，把它放到服务端是纯粹的过度工程。

### 4.2 更重要的是合规角度（这条比技术理由更关键）

**前端实现 = 逻辑完全透明可审计。**

这一点对「我们不是占卜」的定位是**有利**的：
- 审核方若质疑，代码是公开可见的、无害的取余运算
- 用户可以自己看到推演路径（透明 = 可信，也呼应 §5 的仪式感设计）
- 不存在「服务端黑箱在算什么」的想象空间

反过来，**把算法藏进服务端，反而更像「大师在后台做法」**——这恰恰是我们想避开的形象。

### 4.3 什么时候才需要云函数？

只有两个场景，**且都建议复用现有 `family` 云函数加 action，不新建函数**（符合你项目现有的 action 路由约定）：

| 场景 | 需要什么 | 建议时机 |
| --- | --- | --- |
| **伴侣双人对抽比对**（两人各抽一次，看是否一致） | 需要跨设备同步结果 → `family` 加 `action: 'zzjPush' / 'zzjPull'` | v2，可选 |
| **接 AI 生成个性化解读** | 需要云函数代理隐藏 API Key | v2+，且**必须先补深度合成类目 + 算法备案 + AI 标注**（见主报告 §7.4），成本很高 |

**v1 两者都不做。**

### 4.4 曾试过、已回滚：自用层的 AI 解读（2026-09-18）

**当前状态：AI 通道已删除**（客户端入口 + `cloudsync.readingAI` + 云函数 `action: 'reading'` + `reading.js` + 环境变量里的密钥全部移除，云函数已重新部署）。
回滚原因与结论见 `docs/掌中决-页面与交互设计.md` §10.6；本节保留当时的设计要点，供日后若再考虑 AI 时参考：

在**不上架的扩展层**里接了真实大模型，边界如下（务必维持）：

| 项 | 做法 |
| --- | --- |
| 位置 | 云函数 `family` 新增 `action: 'reading'`，实现见 `cloudfunctions/family/reading.js` |
| 模型 | `deepseek-flash`（env `DEEPSEEK_MODEL` 可换） |
